旅日手帖｜實作心得與反思

1. 最終做出了什麼

這次以「第一次日本自由行」為主題，把日本政府觀光局六個官方主題頁整理成LLM Wiki。每個來源都有提案、來源摘要、完整教學文章及可重用概念頁，再由Wiki產生12頁HTML教學簡報。簡報包含章節選擇、上一頁／下一頁、預算試算、行前清單和五題測驗。網址連結和資料查閱日期都留在專案內，方便老師檢查。

2. 為什麼選Graph / Loop

一開始最簡單的作法是直接要求AI做HTML，但這樣內容很難檢查。我採用Graph把過程拆成「官方資料 → Wiki → Wiki檢索 → 證據卡 → 大綱 → 逐頁稿 → HTML → 瀏覽器檢查」。每個節點都有產出檔案，也明定若錯誤要退回哪一個節點。Loop則用來針對單一失敗節點重做，最多三次，避免整份無限重跑。

3. 真正執行時出現的問題

  • 問題一：證據卡連結路徑錯誤。 第一次Wiki Lint得到54/55，原因是slides/cards/裡的相對路徑少了一層../。我沒有重新生成文章，而是修正證據卡產生器，讓連結改到正確的位置，之後重新跑Lint得到55/55。
  • 問題二：Wiki Query中的用詞不夠一致。 第一輪規則式Query只有10/12。查詢期待「不能保證票券省錢」及「手機靜音」的對應敘述，但文章採用不同寫法。經確認JNTO原始內容後，只修正S002與S005教學文章的相關句子，第二輪Query達12/12。這也顯示固定關鍵字測試的限制：字面不符不一定代表事實錯誤。
  • 問題三：本地檔案在測試瀏覽器被封鎖。 初次用file://執行Chromium自動化時，環境回傳ERR_BLOCKED_BY_ADMINISTRATOR。因此在Playwright測試中改用set_content載入相同HTML檔案，而不是修改教學內容本身。測試後12頁切換、預算計算、測驗與行動版排版通過19/19項檢查。

4. 我把檢查往前移到哪裡

如果只在最後才測網頁，證據卡路徑錯誤會很晚才發現。因此我把「Markdown連結與來源ID驗證」提前到證據卡建立後、產生逐頁稿之前。查詢用詞的問題則先在Wiki階段處理，不等HTML完成才回頭改文章。這樣Graph的大範圍回退變少，錯在哪個節點就只修那個節點。

5. 為什麼不能把所有結果都寫成全過

本專案的55/55 Lint是本地靜態檢查，12/12 Query是規則式檢索與證據測試，19/19是Chromium互動測試。它們能證明檔案、連結、公式及互動有實際檢查，但不能替代全新的AI對話對官方來源的獨立忠實度審查，也不能保證幾個月後的交通票價或入境規則仍相同。

6. 人工確認紀錄的差異

S001有使用者對單篇提案的明確批准。S002–S006則因使用者後續說「那你先完成，我再一次下載」，本次將它視為剩餘工作的一次性整體授權；未有逐篇獨立人工核准。雖然每篇仍保留了提案與檢查結果，但若老師嚴格要求逐篇批准，仍需補做逐篇審查並記錄。

7. 本次學到的事

我發現AI能快速整理資料與產出網頁，但真正重要的是先講清楚什麼能用、什麼不能自行推論，以及錯誤出現時要回到哪一個節點。和單純叫AI「幫我做好」相比，拆成可檢查的工作流程比較容易知道問題在哪裡，也比較能說明整份作業是怎麼完成的。下一次我會更早測試來源連結和內容用詞，減少後面修改的時間。
